# Owner Q&A: почему app читает, а API нет · словари рукописного · откуда 3.1 (2026-07-04)

Три вопроса владельца, ответы установлены по коду/логам/git — не по мнению.

## Q1. «Мы договаривались gemini-3.1 не трогать — почему в бенче 3.1-pro-preview?»

`gt-pipeline-bench.mjs` работает в LIVE-режиме: он бьёт в **задеплоенный ПРОД** (`prod
/api/translation/vision-extract`, "the production brain measures itself") — не в локальный код
и не через локальные ключи. `gemini-3.1-pro-preview` в его логе — это модель, которую сервит
**прод (main-ветка)** сегодня. В one-brain ветке `PRIMARY_READER = 'gemini-2.5-pro'`
(modelMatrix.ts:45) и локальный live-shadow шёл на 2.5-pro (подтверждено RESULT_META и
`modelVersion` в прямом API-ответе). **Правило нарушает прод-деплой main, не эта ветка** —
решение по возврату прода на 2.5-pro за владельцем.

## Q2. «Приложения (ChatGPT/Gemini) распознают мои документы, а через API — нет. В чём проблема?»

**В нашем пайплайне, не в ключах/токенах.** Три установленных фактора:

1. **Downscale.** Комментарий в `image-preprocess.ts` документирует это дословно: *«2048 was a
   major "app reads but our API doesn't" cause: a 4–7MB scan got crushed to 2048px → dense
   HANDWRITING fell to ~4–5 px/letter and read empty»*. Cap поднят до 3072, но прод-лог
   СЕГОДНЯ показывает «downscaled from 7.1MB (>4MB edge limit)» — документы всё ещё жмутся.
   В приложении ты зумишь/фоткаешь ФРАГМЕНТ (native-res кроп); наш API-путь шлёт весь лист
   одним жатым кадром.
2. **Строгий контракт.** Приложение отвечает свободным текстом («почти правильно» человек
   принимает); наш путь требует per-field JSON-схему, а скорер — EXACT-match против
   owner-верифицированного GT. Разница между «выглядит прочитанным» и «поле в точности верно».
3. **Рукописный ридер не подключён.** ADR-026 доказал: рукопись читается на NATIVE-res кропах
   (raxtemur бьёт LLM на курсиве). Инструменты в репо (`FIELD_BOX_TEMPLATES`,
   `readHandwrittenRoute`), но подключены только к HTR-sidecar (хост не поднят), и **LLM по
   кропам не ходит**. Это недостающий пролёт моста.

## Q3. «Мы закачивали словарь для укр рукописных документов — почему не используется?»

Полная инвентаризация (агент, file:line):

- **Рукописная confusion-таблица (Т↔П, И↔Н, Ш↔Т, Е↔Є…, 18 пар) РАБОТАЕТ** — default-ON через
  `snapCity` → knowledgeNormalize → арбитраж. Но применяется ТОЛЬКО к местам (place-поля).
- **Villages 17,417 (КАТОТТГ, добавлен 2026-06-22) ЖИВОЙ** — exact-membership в gazetteer для
  city/place ключей. Settlements 458 — exact+fuzzy. Registry 55 — authority/civil-термины.
- **Словаря украинских ИМЁН (имена/фамилии) в репо НЕТ и никогда не коммитился** (git log
  всех добавлений в packages/knowledge проверен). Имена идут через чистую KMU-55
  транслитерацию БЕЗ fuzzy-подгонки к лексикону. Если такой словарь «закачивался» — он не
  попал в репозиторий; дай файл — вайрим как suggestion-сигнал (fuzzy по confusion-таблице).
- **Patronymic** — движок правил (не лексикон): валидация ЖИВАЯ (default-ON), но
  РЕКОНСТРУКЦИЯ отчества от имени отца заперта за `DICTIONARY_AUTOCORRECT_ENABLED` (OFF).
- **Ключевая правда:** все словари постпроцессят текст, который ридер УЖЕ выдал. На рукописи
  GA-LLM фабрикуют → словарям нечего чинить. Словари не были недостающим звеном —
  **недостающее звено = рукописный ридер по native-res кропам** (тот же ответ, что Q2).
